# Group Tags Spec

## Purpose

本規格定義群組成員賽事標記的延遲載入、彙整、篩選與響應式顯示行為，並規範替群友標記已購票時的狀態判斷、資料管理及寫入授權。

## Requirements

### Requirement: 延遲抓取群組標記

系統必須 (SHALL) 採用延遲載入策略。預設僅抓取使用者自身的標記，當使用者在篩選器中切換至「群組所有」時，才抓取群組內其他成員的標記。

#### Scenario: 初始載入頁面

- **WHEN** 使用者進入「我的標記」頁面
- **THEN** 系統預設僅查詢使用者自身的標記，不查詢群組成員的資料

#### Scenario: 切換至群組視圖

- **WHEN** 使用者將第一階段篩選器切換為「群組所有」
- **THEN** 系統查詢使用者所在群組內所有成員 UID 的標記

### Requirement: 標記彙整

系統必須 (SHALL) 將多個群組成員對於同一場賽事（日期）的標記彙整為單一列。

#### Scenario: 多位成員標記了同一場賽事

- **WHEN** 成員 A 與成員 B 皆標記了 7/31 的賽事
- **THEN** 清單中會為 7/31 的賽事顯示單一列
- **AND** 該列在「群友」欄位中顯示兩位成員的名稱
- **AND** 該列整體的標記狀態由最高權重的意向決定（已購買 > 想去）

### Requirement: 二階段標記篩選

系統必須 (SHALL) 提供二階段篩選功能，以便控制資料抓取與檢視範圍。

#### Scenario: 預設的第一階段篩選

- **WHEN** 頁面載入時
- **THEN** 第一階段篩選器預設為「自己」
- **AND** 第二階段篩選器隱藏

#### Scenario: 開啟第二階段篩選

- **WHEN** 使用者將第一階段篩選器切換為「群組」
- **THEN** 第二階段篩選器顯示，並預設為「群組所有」
- **AND** 清單顯示群組內所有成員彙整後的標記

#### Scenario: 篩選特定成員的標記

- **WHEN** 使用者在第二階段篩選器中選擇成員 A
- **THEN** 清單中僅顯示由成員 A 建立的標記

### Requirement: 響應式行動裝置版面

系統必須 (SHALL) 為行動裝置（例如寬度小於 768px）提供經過優化且易於閱讀的版面配置，以避免欄位擁擠。

#### Scenario: 在行動裝置上檢視標記

- **WHEN** 使用者在行動裝置上檢視「我的標記」頁面
- **THEN** 版面會從水平的表格檢視調整為堆疊式或卡片式的佈局
- **AND** 群友資訊會清楚地顯示在新的一行，或是舒適地換行，不會擠壓到賽事日期與對戰資訊

### Requirement: 替群組成員標記已購票

系統 MUST 在 GameModal 保留使用者標記自己已購票的功能，並允許使用者替一位
或多位同群組成員新增或移除自己建立的代購標記。

#### Scenario: 開啟群友選擇清單

- **WHEN** 已登入且有其他群組成員的使用者開啟 GameModal
- **THEN** 系統保留標記自己已購票的按鈕
- **AND** 系統顯示可展開的「替群友標記」操作
- **AND** 清單依 UID 去重且不包含登入者本人

#### Scenario: 沒有其他群組成員

- **WHEN** 已登入使用者沒有任何其他群組成員
- **THEN** 系統只顯示標記自己已購票的操作
- **AND** 系統不顯示空的群友選擇清單

#### Scenario: 替多位群友標記

- **WHEN** 使用者在同一場賽事選取多位同群組成員
- **THEN** 系統為每位成員分別建立由目前使用者擁有的代購紀錄
- **AND** 任一成員的寫入失敗不會移除其他已成功寫入的紀錄

#### Scenario: 取消自己建立的代購標記

- **WHEN** 使用者取消選取先前由自己替群友建立的代購標記
- **THEN** 系統只移除目前使用者擁有的代購紀錄
- **AND** 系統不修改該成員本人或其他購票者建立的紀錄

### Requirement: 彙整有效已購票狀態

系統 MUST 將本人既有的 `ticketPurchased` 布林值與所有有效代購紀錄彙整為
單一已購票狀態，並在所有標記讀取介面使用相同判斷。

#### Scenario: 群友代購形成已購票狀態

- **WHEN** 成員 A 替同群組成員 B 建立某場賽事的代購紀錄
- **THEN** 成員 B 在該場賽事被視為已購票
- **AND** GameModal、GameCard、標記篩選器與「我的標記」顯示一致結果

#### Scenario: 保留既有本人標記

- **WHEN** 賽事資料只有既有的 `ticketPurchased` 為 `true`
- **THEN** 系統仍將該使用者視為已購票
- **AND** 系統不要求搬移或改寫既有資料

#### Scenario: 還有其他有效來源

- **WHEN** 某成員同時有多筆已購票來源且其中一筆被移除
- **THEN** 只要本人標記或至少一筆代購紀錄仍存在，系統仍顯示已購票

#### Scenario: 好友狀態排除本人

- **WHEN** 登入者與群友的標記資料一同載入 GameModal
- **THEN** 好友持票名單不重複顯示登入者本人
- **AND** 每位群友依 UID 最多顯示一次

### Requirement: 代購紀錄寫入授權

系統 MUST 將代購紀錄限制為每位購票者獨立管理的子節點，並在建立紀錄時
驗證購票者與被標記者屬於同一群組。

#### Scenario: 同群組成員建立代購紀錄

- **WHEN** 已登入使用者以自己的 UID 為購票者，替共同群組成員建立紀錄
- **THEN** 資料庫允許寫入並保存用於驗證的共同群組 ID

#### Scenario: 雙方沒有共同群組

- **WHEN** 使用者嘗試替沒有共同群組的另一位使用者建立代購紀錄
- **THEN** 資料庫拒絕寫入

#### Scenario: 修改其他購票者的紀錄

- **WHEN** 使用者嘗試新增、更新或刪除以另一位購票者 UID 為鍵的代購紀錄
- **THEN** 資料庫拒絕寫入

#### Scenario: 購票者離開群組後移除自己的紀錄

- **WHEN** 購票者離開原共同群組後刪除自己先前建立的代購紀錄
- **THEN** 資料庫允許刪除自己的子節點

#### Scenario: 被標記者清除錯誤紀錄

- **WHEN** 被標記者移除套用在自己賽事標記下的代購紀錄
- **THEN** 資料庫依既有資料擁有者權限允許刪除
