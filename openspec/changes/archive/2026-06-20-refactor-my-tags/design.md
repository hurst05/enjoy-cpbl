# Design

## Context

目前的「我的標記」功能僅抓取並顯示登入使用者的標記。然而，由於許多使用者會與好友群組共同協調觀賽行程，單獨檢視每個人的標記相當不便。使用者希望能有整合的視圖，一眼看出群組的整體意向（誰想去、誰已買票）。目前的系統會將標記與使用者的 `uid` 存在 Firebase 中，同時我們也具備群組系統來記錄使用者所屬的群組。我們需要為當前作用中群組的所有成員彙整標記資料。

## Goals / Non-Goals

**Goals:**

- 支援抓取所有群組成員的標記資料，但採用延遲載入（預設只抓取自己）。
- 提供二階段的篩選介面：先選擇「自己」或「群組所有」，選取後者才顯示進階的「特定成員」篩選。
- 依日期（賽事）彙整標記，使單一列能顯示多人的意向。
- 在整合單一賽事的視覺狀態時，優先顯示「已購買」而非「想去」。
- 優化行動裝置的版面配置，避免新加入的資訊造成畫面過度擁擠。

**Non-Goals:**

- 標記變更時的群組聊天或通知功能。
- 跨群組的標記共享。

## Decisions

- **Data Fetching:** 採用延遲載入策略。初始載入頁面時，預設只抓取使用者自身的標記（`where("uid", "==", currentUser.uid)`）。當使用者在第一階段篩選器切換為「群組所有」時，才觸發另一次 Firebase 查詢，利用 `in` 運算子抓取其作用中群組內所有成員的標記資料。
- **Aggregation Logic:** 在客戶端抓取資料後，依據賽事 ID（或日期）將標記進行分組。對於每一場賽事，我們會收集一個包含成員及其標記類型的陣列。該列整體的標記「狀態」將被設定為最高權重的狀態（`已購買` > `想去`）。
- **Filter UI:** 設計為二階段篩選：
  - 第一階段下拉選單：選項為 `'self'`（預設）與 `'group'`。
  - 第二階段下拉選單：當第一階段選取 `'group'` 時顯示。選項包含 `'all'`（群組所有）以及特定成員的 `uid`。
- **List Columns (Desktop):** 新增一個「群友」欄位。對於彙整後的資料列，此欄位會顯示有標記該賽事的群組成員名稱（例如："A, B, C"）。
- **Mobile Layout:** 在較小螢幕（例如寬度小於 768px）上，改用堆疊式或卡片式的佈局取代水平表格，避免欄位受到擠壓。群組成員的資訊將會在卡片內換行顯示。

## Risks / Trade-offs

- **Risk**: 若群組人數多且標記數量大，可能會增加 Firebase 的讀取次數。
  - Mitigation: 群組規模通常較小。Firestore 的 `in` 查詢限制為最多 30 個值，這對一般的好友群組來說已經足夠。
- **Risk**: 若顯示過多成員，清單視覺上會顯得雜亂。
  - Mitigation: 如果成員名稱過長，則截斷名稱或使用縮寫處理。
