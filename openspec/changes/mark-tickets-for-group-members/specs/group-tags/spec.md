# Group Tags Delta Spec

## ADDED Requirements

### Requirement: 替群組成員標記已購票

系統 MUST 在 GameModal 保留使用者標記自己已購票的功能，並允許使用者替一位
或多位同群組成員新增或移除自己建立的代購標記。

#### Scenario: 開啟群友選擇清單

- **WHEN** 已登入且有其他群組成員的使用者開啟 GameModal
- **THEN** 系統保留標記自己已購票的按鈕
- **AND** 系統顯示可展開的「替群友標記」操作
- **AND** 清單依 UID 去重且不包含登入者本人

#### Scenario: 沒有其他群組成員

- **WHEN** 已登入使用者沒有任何其他群組成員
- **THEN** 系統只顯示標記自己已購票的操作
- **AND** 系統不顯示空的群友選擇清單

#### Scenario: 替多位群友標記

- **WHEN** 使用者在同一場賽事選取多位同群組成員
- **THEN** 系統為每位成員分別建立由目前使用者擁有的代購紀錄
- **AND** 任一成員的寫入失敗不會移除其他已成功寫入的紀錄

#### Scenario: 取消自己建立的代購標記

- **WHEN** 使用者取消選取先前由自己替群友建立的代購標記
- **THEN** 系統只移除目前使用者擁有的代購紀錄
- **AND** 系統不修改該成員本人或其他購票者建立的紀錄

### Requirement: 彙整有效已購票狀態

系統 MUST 將本人既有的 `ticketPurchased` 布林值與所有有效代購紀錄彙整為
單一已購票狀態，並在所有標記讀取介面使用相同判斷。

#### Scenario: 群友代購形成已購票狀態

- **WHEN** 成員 A 替同群組成員 B 建立某場賽事的代購紀錄
- **THEN** 成員 B 在該場賽事被視為已購票
- **AND** GameModal、GameCard、標記篩選器與「我的標記」顯示一致結果

#### Scenario: 保留既有本人標記

- **WHEN** 賽事資料只有既有的 `ticketPurchased` 為 `true`
- **THEN** 系統仍將該使用者視為已購票
- **AND** 系統不要求搬移或改寫既有資料

#### Scenario: 還有其他有效來源

- **WHEN** 某成員同時有多筆已購票來源且其中一筆被移除
- **THEN** 只要本人標記或至少一筆代購紀錄仍存在，系統仍顯示已購票

#### Scenario: 好友狀態排除本人

- **WHEN** 登入者與群友的標記資料一同載入 GameModal
- **THEN** 好友持票名單不重複顯示登入者本人
- **AND** 每位群友依 UID 最多顯示一次

### Requirement: 代購紀錄寫入授權

系統 MUST 將代購紀錄限制為每位購票者獨立管理的子節點，並在建立紀錄時
驗證購票者與被標記者屬於同一群組。

#### Scenario: 同群組成員建立代購紀錄

- **WHEN** 已登入使用者以自己的 UID 為購票者，替共同群組成員建立紀錄
- **THEN** 資料庫允許寫入並保存用於驗證的共同群組 ID

#### Scenario: 雙方沒有共同群組

- **WHEN** 使用者嘗試替沒有共同群組的另一位使用者建立代購紀錄
- **THEN** 資料庫拒絕寫入

#### Scenario: 修改其他購票者的紀錄

- **WHEN** 使用者嘗試新增、更新或刪除以另一位購票者 UID 為鍵的代購紀錄
- **THEN** 資料庫拒絕寫入

#### Scenario: 購票者離開群組後移除自己的紀錄

- **WHEN** 購票者離開原共同群組後刪除自己先前建立的代購紀錄
- **THEN** 資料庫允許刪除自己的子節點

#### Scenario: 被標記者清除錯誤紀錄

- **WHEN** 被標記者移除套用在自己賽事標記下的代購紀錄
- **THEN** 資料庫依既有資料擁有者權限允許刪除
